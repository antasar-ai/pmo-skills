# Conceptual model

The user wants to understand something and think with it afterwards. Give them a model they can rebuild: the parts, how the parts relate, where the edges are, and the words the field uses.

## Before you start

Find out what the user already knows and which system they understand well. Find out which field the topic belongs to and use that field's names. Reuse existing vocabulary before inventing any.

Separate what is observed, what is proposed, and what is unknown. Say which is which.

## The thinking

**Primitives.** The smallest parts of the domain that cannot be broken down further. Everything else is built from them.

**Relations.** How primitives connect: what owns, contains, triggers, depends on, or produces what. With direction.

**Boundaries.** What sits outside, and the "is not" statements for the things it gets confused with.

**Layers.** From primitives up through the composites to the thing people talk about. A pyramid the user can walk up and down.

**System map.** The whole on one page: parts, relations, flows in and out. A tree or Mermaid when it helps.

**Analogy.** One system the user already knows, mapped onto this one, with the line where the analogy breaks. An unmarked break misleads more than no analogy.

**Stress test.** Take a concrete case and run it through the model. If the case does not fit, the model is wrong, not the case. Fix the model.

## Ask back

When a term is fuzzy or overloaded, ask instead of guessing: "You said account. Do you mean the customer or the user?" When the user's mental model conflicts with the field's, say so and ask which one to keep.

## Terms

Close with a short table: term, meaning in this model, what it is often confused with. Field-standard names, overloaded ones marked.

## Deliver

Return a model note as short as the topic allows: one line what it is, primitives, relations, layers, the map, the analogy with its break point, the terms. Apply write-human to the prose.
